# 学习笔记 · 评测指标与面试追问应对

> 这份文档写给项目作者自己复习用：把 README 评测节背后每一个数字、每一个可能被面试官追问的问题，掰开揉碎讲清楚。读文档建议顺序：先读 §1 打底，再读 §2 消融，§3-§5 是三个"必被追问"的预案。

## 1. 评测指标到底是什么（通俗版）

### 1.1 Hit@5 —— 找没找到

把问题丢进检索器，它返回排好序的资料列表。**Hit@5 问的是：正确的那份资料有没有出现在前 5 条里。** 出现了算"命中"，没出现算"漏了"。

比喻：在图书馆找"武器价格"，管理员抱来一摞书，前 5 本里有没有你要的那本？有 = 命中。

本项目：17 个检索题里 12 个命中 → 70.6%。

### 1.2 MRR —— 排得靠不靠前（重点，也是你最容易讲错的地方）

MRR = **Mean Reciprocal Rank，平均倒数排名**。它不是精确率！

规则：正确资料排第 1 名记 1 分，排第 2 名记 1/2 = 0.5 分，排第 3 名记 1/3 ≈ 0.33 分……越靠后分越低，没进前 5 记 0 分。所有题目的得分取平均就是 MRR。

比喻：同样是"找到了"，管理员第 1 本就递给你（1 分）和翻了 4 本才递给你（0.25 分），体验完全不同。MRR 衡量的就是这个"第几本就递到"。

**为什么 MRR 从 0.882 降到 0.796（旧数据）/ 0.637 降到 0.598（消融数据）？**

旧管线（纯向量）几乎每题的正确资料都排第 1（分数接近"满分 1.0"）；开了混合检索后，BM25 这个"关键词搜索器"会把一些**沾边但不核心**的资料也拉进前排——比如教程文档里顺带提了一句 Jett，用户问 Jett 时它也冲到了前几名。而入门级的重排模型纠不动这种错位，于是正确资料的"名次"平均被挤后了一点，MRR 就降了。

注意：**MRR 降 ≠ 找不到（Hit@5 没降）≠ 答错**。它只是"正确答案的名次平均往后挪了 1-2 位"。

### 1.3 精确率 vs 召回率 —— 你的"召回比精确重要"对不对？

先分清三个概念（用"捞鱼"比喻）：

| 指标 | 问的问题 | 漏捞鱼？ | 捞到垃圾？ |
|------|------|------|------|
| **召回率**（Recall） | 该找的都找到了吗？ | 扣分 | 不扣 |
| **精确率**（Precision） | 找到的里有用吗？ | 不扣 | 扣分 |
| **MRR** | 最好的排第几？ | 排名靠后扣分 | 挤占前排扣分 |

你说"**召回比精确重要，宁愿精确率低一些也要召回到位**"——方向是对的，而且是检索工程的常见取舍：**宁可多捞一些交给后面过滤，也别一开始就漏**。混合检索的设计动机正是这个：BM25 兜住纯向量可能漏掉的关键词命中。

但要补一层：在 RAG 系统里"宁多勿漏"只在**检索层**成立，因为后面还有重排序帮忙过滤；到了**最终答案层**，规则反过来了——**"答错"比"不答"严重得多**，所以拒答兜底（宁可说"我不知道"也不瞎编）是精确率思维的胜利。一句话总结：**检索层保召回，答案层保精确，两层分工不同。**

（另外提醒：你说的"失主的自我判断最准确"是失物招领系统里的逻辑——那是人对人的匹配确认。RAG 项目里没有失主，面试时注意别把两个项目的概念讲串了，这两个项目都是你简历上的，面试官很可能两个都问。）

### 1.4 "75%（24/32）"里的 32 是什么

32 = **评测集里所有题目"期望关键词"的总个数**。

评测集每道题除了指定"应该命中哪份文档"（expected_docs），还列了"答案里应该出现哪些词"（expected_keywords）。比如题目"正义手枪多少钱？伤害是多少？"期望关键词是 `["800", "55", "159"]` 三个词。把 17 道生成题的关键词全加起来 = 32 个。

开启 LLM 生成后，看答案文本里实际包含了其中几个词：命中 24 个 → 24/32 = 75%。它衡量"答得全不全"，是生成质量的粗代理（不是智能评测，只是关键词命中，所以它高也不代表答案通顺）。

这个数字是 v3.0 上线时（2026-09-11）带 LLM 跑出来的；当前智谱密钥 401 失效，换新密钥后跑 `python scripts/evaluate_rag.py --mode hybrid`（不带 `--skip-llm`）即可复测。

### 1.5 为什么 94.1% 变成了 70.6% —— 数字漂移的活教训

README 旧版写 Hit@5 94.1%，今天实测 70.6%（12/17）。两个原因：

1. **口径**：旧数字的分母其实是 17 不是 20（3 道拒答题只算拒答正确率，不进检索指标）——但旧 README 没写口径，读者会拿 20 当分母去猜；
2. **知识库变过**：评测数字依赖知识库内容。9 月中知识库 12 篇文档都改过内容，向量排序随之变化，旧数字就作废了。

教训写进 README 了：**评测数字必须带日期和知识库版本，改库必须重跑**。这也是面试加分点——你能主动讲"我的评测数字会失效，所以我标注了评测环境"，比背一个漂亮数字强得多。

## 2. 消融实验：每段管线到底有没有用

### 2.1 什么是消融实验

把系统的零件一个个关掉，看指标掉不掉：关掉掉分 = 这零件有用；关掉不掉分 = 这零件是摆设（或者它的价值场景没被测到）。比喻：拔掉一根线看灯灭不灭，灭了才说明灯是它点的。

### 2.2 实测结果（2026-09-18，skip-llm）

| 组合 | Hit@5 | MRR | 拒答正确率 |
|---|---|---|---|
| A. 纯向量 | 70.6% | 0.637 | 33% |
| B. 纯向量+重排 | 70.6% | 0.608 | **100%** |
| C. 混合检索 | 70.6% | 0.637 | 0% |
| D. 混合+重排（v3） | 70.6% | 0.598 | **100%** |

### 2.3 三条结论（面试可以直接讲）

1. **重排序是拒答能力的唯一来源**：B、D 都是 100%，A、C 最高 33%。机制：CrossEncoder 的分数区分度好（无关 ≈0.50，相关 ≥0.67），0.60 阈值能切开；原始向量相似度区分度差，切不开。
2. **混合检索在当前知识库规模下零检索收益**：Hit@5 一分没涨，MRR 还被 BM25 的弱关联块拖低 0.039。保留它的理由是给未来知识库扩容预留架构，不是因为现在有用。
3. **查询改写测不出效果是评测集的局限**：单轮问题没有指代可消解，它的战场在多轮对话——这套评测集压根没考它。面试被问"改写有什么用"时，要主动说"我的单轮评测覆盖不到它，这是评测集盲区"。

### 2.4 这组消融的最佳用途

面试官若质疑"三级管线是不是过度设计"，标准答案就是这张表：**"我做了消融，拒答收益全部来自重排；混合检索是架构预留；我也因此知道该优先优化什么（换更强 reranker / 扩评测集），而不是无脑堆模块。"** 敢承认哪段没用，比吹全都有用可信十倍。

## 3. 拒答阈值 0.60：怎么调的，上线后怎么监控

### 3.1 现状与风险（先自曝）

0.60 来自：重排分数分布中，无关问题 ≈0.50、相关问题 ≥0.67，取中间。**风险**：这组观察来自评测集那 20 题，阈值在它上面调、又在它上面报 100%——"用考卷练题再考同一张卷"，换一批新题分数可能漂移。这是这套评测最大的方法学软肋，面试前必须心里有数。

### 3.2 短期可做的三步（不用改架构）

1. **切分验证集**：把评测集按 7:3 分成"调参集"和"验证集"——阈值只在调参集上调，数字在验证集上报。哪怕只有十几题，也比自证循环强；
2. **记录分数分布**：评测脚本已输出每题 top 来源和分数，把"相关/无关"两组分数画成直方图，确认 0.60 落在两坨分布的中间谷地，而不是切在某一坨的山坡上；
3. **边界用例回归**：故意准备 5-10 个"半相关"问题（比如"CS 的 AK 多少钱"），看分数落在哪，确认边界行为符合预期。

### 3.3 上线后的监控方案（面试话术）

- **埋点**：每次问答记录"重排最高分 + 是否拒答"两个字段（审计日志里已有基础）；
- **看分布漂移**：按天/周聚合最高分分布。健康状态是双峰（相关一坨、无关一坨，中间隔着阈值）；如果分布整体移动（比如用户问起新版本英雄，措辞变了），峰形会偏移；
- **漂移警报**：拒答率突然飙升（分布整体左移）或归零（阈值失效）都报警；
- **定期回归**：知识库每次更新后重跑评测集，数字与上次对比，跌幅超 5 个百分点即人工审查。

## 4. 企业要"文档级权限"怎么办

### 4.1 先分清两件事

- **kb_id 隔离（本项目已有）**：不同业务/租户各建各的知识库，A 部门查不到 B 部门的库。这是**库与库之间**的隔离。
- **文档级权限（本项目没有）**：同一个库里，"薪资制度.pdf"只有 HR 能查，普通员工查"薪资"时根本不该检索到它。这是**库内文档与文档之间**的隔离。

面试时如果只答 kb_id，懂行的会立刻追问这一层。标准答案是承认差距 + 给出方案：

### 4.2 方案（从易到难三层）

1. **元数据过滤（第一层，改动最小）**：入库时给每个文档块打权限标签（`dept=hr`、`level=manager`），查询时先取用户权限，把过滤条件拼进向量检索的 where 子句（ChromaDB 支持 metadata where 过滤）。缺点：过滤逻辑自己维护，标签一多就乱。
2. **外部权限源对齐（第二层，生产主流）**：企业权限通常已在 AD/LDAP/OA 系统里。检索时先问权限系统"这个用户能看哪些文档 ID"，再把允许清单传给检索器做过滤（类似大厂 RAG 里常见的 ACL 管道）。关键原则：**权限判断永远以权限系统为准，RAG 只做执行者**，否则权限更新后向量库会滞后。
3. **多租户/多集合（第三层，重隔离）**：敏感等级极高的文档单独建 collection 甚至独立向量库实例，物理隔离，宁可牺牲一点检索的跨域召回。

配套还要答两点：**审计**（谁在什么时候查到了什么，本项目 audit 日志已有雏形）和**索引侧安全**（文档删除/权限收紧后，旧向量必须同步删掉，否则"人看不见了但 AI 还能搜出来"是最常见的事故）。

## 5. "降低幻觉"缺的证据与补法

README 卖点之一是"降低幻觉"，但目前的证据只有间接的：检索有依据（Hit@5）、答不出就拒答（100%）、答案带来源。**缺的是直接证据：答案本身有多少比例忠于检索到的资料**——这个指标叫 **faithfulness（忠实度）**。

补法（工作量从小到大）：

1. **人工抽检**：拿 30 条真实回答，人工判断每条是否与来源一致，给个忠实率。半小时的活，聊胜于无；
2. **RAGAS 自动评测**：开源的 RAG 评测框架，用 LLM 给"忠实度 / 答案相关性 / 上下文相关性"打分。需要有效的 LLM 密钥；
3. **引用对齐校验**：要求生成时每句话标注引用编号，程序校验"这句话的信息是否真的出现在被引文档块里"。工程量最大，但最硬核。

面试话术："当前用机制（检索依据 + 拒答 + 来源展示）压幻觉，量化忠实度评测是 roadmap 项，计划用 RAGAS 补。"
